# The `dokkit` program

One Go binary, `dokkit`. The same file is the command-line tool and the thing that stays running on a machine.

## Commands

| Group | Command | Does |
|---|---|---|
| In an app repo | `dokkit init` | Asks what the app is and writes `dokkit.toml`. |
| | `dokkit check` | Validates the file, runs every check once on this machine, prints exactly what would be sent. Needs no server. |
| | `dokkit apply` | Sends the file to Dokkit. |
| Jobs | `dokkit run --job <name> -- <command>` | Runs the command and reports start, finish, exit code, duration and the last lines of output. Exits with the command's own exit code. |
| | `dokkit ping <name> [start, ok or fail]` | For a job that cannot be wrapped. |
| | `--service <slug>` on either | The service the job is declared under. Without it the program finds the `[[job]]` of that name in the `dokkit.toml` files it reads. |
| This machine | `dokkit enrol <address> <token>` | Trades a one-time token for this machine's key and stores the server's certificate fingerprint. |
| | `dokkit status` | What this machine is watching and when it last reported. |
| | `dokkit doctor` | Can it reach the server, does the certificate match, does the server know the key, is the clock right; each failure says what it is and the one thing to do. |
| | `dokkit version` | Prints the version this build was made as. |
| Discovery | `dokkit scan` | Looks at what is on the machine and writes a proposal file. Sends nothing. |
| | `dokkit propose` | Sends the proposal file to be accepted in the interface. |
| | `dokkit import seq --from <address>` | Copies a Seq server's stored events into Dokkit's logs, oldest first, with their own times. Resumable; `--dry-run` counts and sends nothing. See `docs/moving-over.md`. |
| Staying running | `dokkit watch` | Runs in the foreground under a login. An ordinary program: no administrator, no service. |
| | `dokkit watch --background` | The same, left running with no window. |
| | `dokkit folder add <path>`, `remove <path>`, `list` | Sets the folders `dokkit watch` reads `dokkit.toml` files from. With the service installed it changes the service's list, which needs an administrator or root; otherwise it changes the signed-in person's own. |
| | `dokkit imessage on`, `off`, `status`, `test <recipient> [words]` | Lets this Mac send iMessages when the server asks, or sends one now to try it. |
| | `dokkit startup on`, `off` | Starts `dokkit watch --background` each time this person signs in. No administrator. Windows only. |
| | `dokkit service install`, `uninstall`, `update`, `start`, `stop` | Runs as a service on Windows, Linux (systemd) or macOS. Needs an administrator, or root, once. |
| | `dokkit updater install`, `uninstall`, `run`, `status`, `rehearse <folder>` | A separate updater that moves the program, and the server on the machine that hosts it, to a signed release approved in the interface. See `updates.md`. |

## Three levels

Each is a choice. None is a requirement for the next.

| Level | Needs | What it does |
|---|---|---|
| Declared | No administrator, no scan | Checks only what is listed in `dokkit.toml` files or added in the interface. |
| User-space | No administrator | `dokkit watch` under a login. Sees ports, processes, disks and readable logs. Stops at logoff and cannot restart services. |
| Installed service | Administrator, once | Survives logoff, restarts allow-listed services, scans once a day and when asked. |

## How it behaves

**No open port, at any level.** `dokkit` only makes outbound requests. Work arrives over a request it holds open to the server.

**Nothing is lost when the server is unreachable.** Everything goes to a spool folder on disk first and is sent from there. A log file's read position only moves forward after the server confirms it has the lines. The spool has a size cap, 500 MB by default, set with `DOKKIT_SPOOL_MB` or `spool_mb` in the saved configuration. When it is hit, the oldest goes and the number dropped is reported to the server as a warning log line. A spooled batch the server keeps answering with an error is set aside (renamed `.rejected`) once the server has taken others since, so it does not hold up the rest. A batch the server answers `413` (too large) is halved and sent in pieces, down to one line. A batch it answers `422` for is split the same way until the lines it will not take are alone, and a line the answer names as refused is taken out of the batch; only those lines are written to a `.rejected` file in the spool, each with the reason, and the rest are delivered. A single line the server still finds too large is cut to 64 KiB of message (its `fields` are dropped when over 64 KiB), with a marker at the end of the message. Lines cut or set aside are counted per file and reported to the server as a warning log line. A log file's lines that draw a server error (`500` or other) are never skipped: the position stays, and the same lines are tried again after a growing wait of up to five minutes.

**`dokkit run` and `dokkit ping` work with or without `dokkit` running.** If it is running they leave their report in the spool folder. If not, they send it themselves.

**It only does what it is told by name.** The server can ask the program to fetch the newer copy of itself, to look itself over again, and a Mac to send an iMessage, and nothing else. It never runs a command someone defined, and a found job's command line is only shown.

**It sends an iMessage only from a Mac told it may.** Alerts by iMessage go out through a Mac signed in to Messages. The server asks with a built-in piece of work, `dokkit:imessage`, naming the recipients and the text; each is sent through the Messages app with `osascript`, the recipient and text passed as arguments and never as part of the script, and the run gets one line per recipient. `dokkit imessage on` records in the saved configuration (`imessage`) that this Mac may, and it is off by default; without it, on any other system, or with no recipient or text, the machine refuses the work. A recipient that is not a phone number or an email address is not sent to, and a text is cut at 1000 characters. `dokkit imessage test <recipient>` sends one from this Mac without the server. The first send makes macOS ask once, on the Mac's screen, whether `dokkit` may control Messages; a signed build is needed for macOS to remember the answer.

**It never asks for antivirus to be turned off.** The declared and user-space levels exist so that getting started never needs an exception.

**A scan writes a proposal.** Nothing a scan finds is watched until it is accepted.

## What a scan looks at

| Part | Finds |
|---|---|
| Services | Installed services and their state. |
| Ports | What is listening, and which program owns it. |
| Containers | Running containers and their images. |
| Sites | Sites configured in a web server. |
| Disks | Volumes and free space. |
| Jobs | Scheduled work, to be watched and never run: Task Scheduler tasks on Windows; cron entries and systemd timers on Linux; cron entries and launchd jobs on macOS. |
| Declarations | `dokkit.toml` files in the allowed folders. |

Each part can be switched off with a flag. The proposal file shows everything found before anything is sent.

A scan never reads file contents, credentials, browser data, or another program's memory. The one exception is the files cron itself reads (the account's crontab, `/etc/crontab`, `/etc/cron.d`, and for root `/var/spool/cron`), which are the schedule, and the control group of a listening process on Linux (`/proc/<pid>/cgroup`, which names its service). A command line shown for a job has anything after `password`, `secret`, `token` or `api_key` replaced by `***` and is cut at 300 characters.

**What a scan costs.** It runs a handful of the machine's own listing commands (on Windows `sc`, `netstat`, `tasklist`, `schtasks`, and `docker` and `appcmd` where they are installed; on Linux `systemctl`, `ss`, `crontab`, `docker`, and `dpkg-query`, `apt-mark` or `rpm` to ask which package owns a unit file), reads the registry values named under Origin on Windows,, which together take a few seconds, reads the files named above, changes nothing, and sends one document of at most 2000 findings.

### Jobs

Each job is proposed with a name, its schedule turned into a five-field cron line, the last run time and last result where the system records them, and its command line, shown so a person recognises it. A cron line is read as UTC, so a schedule in the machine's local time is converted with the offset the machine has at the moment of the scan, and the proposal says so. A schedule that cannot be put in a cron line (at logon, on idle, every 14 days, several times, a day such as the last of the month) is proposed with no schedule and a note saying why; such a job is noticed when a run fails and not when a run does not happen.

| System | Where jobs are found | Last run and result | Cannot be seen by an unprivileged account |
|---|---|---|---|
| Windows | `schtasks /query /fo csv /v`. Tasks under `\Microsoft\` and disabled tasks are left out. | Yes, from Task Scheduler. | Tasks only administrators or the system account can read are not listed. |
| Linux | The account's `crontab -l`, `/etc/crontab`, `/etc/cron.d/*` where readable, and `systemctl list-timers --all` (timers named `systemd-*` are left out). | Timers only. Cron does not record runs. | Other accounts' crontabs (`/var/spool/cron`), user timers (`systemctl --user`), and the scripts in `/etc/cron.daily` and the like. |
| macOS | cron as on Linux, and launchd jobs with a calendar or interval schedule in `~/Library/LaunchAgents`, `/Library/LaunchAgents` and `/Library/LaunchDaemons` (Apple's own are left out). | Launchd only, the last exit status. | Jobs in directories the account cannot read. |

The proposal's `notes` say what the scan could not see; the Found page shows them with the jobs.

An accepted job waits for its first report and is not judged late until it has had one. How its runs are reported depends on where it was found:

- Windows Task Scheduler tasks and systemd timers are watched from the machine's own record. Each minute `dokkit watch` fetches the accepted jobs of this kind (`GET /records`), reads each one's last run time and last result (`schtasks /query /tn`, or `systemctl show` for the timer and its service), and reports a run when they differ from the last reading, with the time the system gives and, for a timer, how long the run took. The first reading after a job is accepted only sets the starting point, so the first run reported is the next one. Nothing about the task or timer changes. The last readings are kept in `records.json` in the spool folder.
- Cron entries and launchd jobs need the wrapper: the Found page shows the line to use, `dokkit run --job <name> -- <command>`, or `dokkit ping <name> ok` (and `fail`) at the end of the script.

Containers are proposed only when they publish a TCP port on the machine, as a service with a `tcp` check on that port; no check type looks inside a container, so one with no published port is not listed. IIS sites are proposed with an `http` check on the address of their first http or https binding. Sites of nginx and Apache are found by name only (their configuration files are not read), so they are not proposed. Disks are watched as the machine's own readings and are not proposed.

### Origin

Every service, port, job, container and site a scan sends carries `origin` and `why`. `why` is one short line naming the fact the decision came from. The scan still sends everything; the server uses `origin` to hide the first kind by default.

| `origin` | Means |
|---|---|
| `system` | Ships with the operating system: its own services, the ports they listen on, its own scheduled jobs. |
| `software` | Installed by other software: an RMM agent, a vendor updater, a database, a driver utility, a Microsoft product that is not part of Windows (Office, Edge update, OneDrive, SQL Server). |
| `yours` | Set up by a person: NSSM-wrapped services, runners, their own units, cron lines and scripts. Also anything whose owner the scan cannot tell: nothing unknown is ever `system`. |

The decision is made from facts the machine gives the account the scan runs as, never from a list of names. Dokkit's own service, updater timer, task, daemon, cron line and start script are `software` with the reason "Dokkit itself".

**Windows services.** The executable comes from the `ImagePath` value of `HKLM\SYSTEM\CurrentControlSet\Services\<name>`; below `Parameters`, `Application` is the real program of an NSSM-wrapped service and `ServiceDll` the library a service host (`svchost.exe`) loads. Local Service may read these keys (every service key grants read to Everyone, Users, Authenticated Users or the service group; a few `Parameters` keys do not, and then the host's own location decides). Executable under the Windows folder, a per-user service instance (name ending in `_` and hex digits) and the Windows Defender, Microsoft Defender and WSL folders are `system`; a vendor's executable in `Windows\System32\DriverStore` is `software` (a driver utility). `nssm.exe`, a GitHub Actions runner and an executable outside `Windows`, `Program Files`, `Program Files (x86)` and `ProgramData` are `yours`; an executable in a user's `AppData\Local` or `AppData\Roaming` folder inside a vendor folder (where installers put per-user programs) is `software`, unless it is a script engine; everything under `Program Files*` and `ProgramData` is `software`.

**Windows ports.** The owning process id comes from `netstat`. If that process, or the process that started it (NSSM starts the real program), is a service from `tasklist /svc`, the port takes that service's origin (the least hidden one, if a host runs several). The System process is `system`. Otherwise the process's program file (`QueryFullProcessImageName`, readable for the processes this account may query) is judged by its place as above; if it cannot be read, a program that exists under `System32` by that name is `system`; anything else is `yours` with the reason "owner not known".

**Windows scheduled tasks.** A task whose program is under `Program Files*` or `ProgramData` is `software`, also under `\Microsoft\`. Under `\Microsoft\` otherwise, or running a program from the Windows folder, is `system`. For a shell or script engine (`cmd`, `powershell`, `wscript`, `python`) the script it is given is judged instead. A task whose author is a company or vendor name (not an account such as `PC\someone`) and a task in a user's app data vendor folder are `software`; the rest are `yours`, as are tasks whose program cannot be read (a COM handler).

**Linux services and timers.** `systemctl show -p FragmentPath` gives the unit file and its links are followed. A file under `/usr/lib/systemd/system` or `/lib/systemd/system` (also reached by a link from `/etc/systemd/system`) is `system` when no package owns it or when its package is part of the base system, otherwise `software` ("Unit shipped by package ..."). On Debian and Ubuntu `dpkg-query -S` gives the package, and a package is base when its `Priority` is `required`, `important` or `standard`, or when `apt-mark showauto` lists it (it came in as a dependency and nobody chose it by name); other packages are add-ons. With `rpm`, the owner is found with `rpm -qf` and every owned unit in the distribution's folder is `system`. A unit in `/etc/systemd/system` that is not a link into those folders is `software` when a package owns it and `yours` when none does; units under `/usr/local`, `/opt` and a home folder are `yours`; units systemd generates (`/run/systemd/generator`) are `system`.

**Linux ports.** The listening process's service comes from its control group, which `ss -p` names only for processes the account may see; the port takes that unit's origin. A process in a login session is `yours`; an owner that cannot be told is `yours` with "owner not known".

**Cron.** An account's own crontab is `yours`. Lines of `/etc/crontab` that run `run-parts` are `system`, other lines there are `yours`. A file in `/etc/cron.d` that a package owns follows the same package rule as units, and any other is `yours`.

**QNAP.** On a QNAP NAS (`/etc/config/uLinux.conf` exists) the crontab is judged by the program of each line: add-ons (`.qpkg`, `/mnt/ext/opt`, or the `#_QSC_` and `#_SA_` tags the QNAP app center writes) are `software`; a program under `/share/`, `/home/`, `/root/` or `/tmp/` is `yours`; the rest of the file system is the firmware and is `system`.

**macOS.** A `com.apple.*` label or a program under `/System`, `/usr/libexec` or `/Library/Apple` is `system`. A program under `/Applications` is `software`. A program under `/usr/local` or a home folder, or a job file in a home folder, is `yours`. Other jobs in `/Library/LaunchDaemons` and `/Library/LaunchAgents` are `software`.

**Containers and sites** are `yours`.

An older program sends no `origin`; the server keeps it as unknown, shows it and never hides it.

### When a scan runs

A program running as the installed service, or as `dokkit watch`, scans on its own about two minutes after it starts and then once a day, and sends the proposal. The Found page has a Look again button for each machine, which queues the built-in piece of work `dokkit:scan`. It carries no parameters; the program runs the same read-only scan, sends the proposal, and answers with the counts. An older program that does not know it answers with a refusal, which the page shows as "this machine's program is too old to be asked". The API is `POST /api/v1/machines/:id/scan` (scope `act`), and the AI tool is `scan_machine`.

## Updates

`dokkit` never updates itself, and never replaces its own file. The updater below is the way a machine is moved to a new release. The built-in update described here only fetches. Under the Windows service the built-in update fetches nothing either, for the same reason as on Linux: an administrator puts the newer `dokkit.exe` on the machine and runs it with `service update`. Under the Linux service the built-in update fetches nothing: a file the `dokkit` user could write is not one root should run, so the run says to install the newer program as root (run `get.sh` again) and then run `dokkit service update`. A `dokkit watch` under a login fetches only to its own user-owned copy and says the same about the service: an administrator runs `get.sh` as root, then `dokkit service update`; it never tells root to run a file a login owns. Without the updater that is the way an installed Linux service is updated; `service update` also works when `get.sh` has already put the new file in `/usr/local/bin`, and restarts the service. The interface shows when a machine is behind the copy the server holds. A person can ask that machine to fetch the newer copy, the file is left in an `update` folder beside the spool, and the run says where it is and its SHA-256. When the machine's configuration has `update_sha256`, a fetched file with another hash is removed, and so is any copy left in the `update` folder by an earlier fetch. `dokkit enrol` keeps the `update_sha256` already in the configuration file (`config.json` in the machine's configuration folder). Without the updater the update is finished on the machine by a person, as an administrator: `"<that file>" service update` stops the service, puts the newer copy in its place and starts it. A program that swaps itself for whatever a server sends it, while running as the system account, is the thing this avoids.

`dokkit updater install|uninstall|run|status|rehearse <folder>` installs and drives a separate updater that moves the program, and on Windows the server on the machine that hosts it, to a signed release a person approved in the interface. It works on Windows (a scheduled task), Linux (a systemd timer, or a root crontab line where there is no systemd, as on a QNAP NAS) and macOS (a LaunchDaemon); on Linux and macOS it is installed by root, finds how the program is kept (system or user unit, LaunchAgent, or a plain `watch --background`) and restarts it that way, and the program keeps running as its own account. The program itself still never replaces its own file. `dokkit version` prints the version a build was made as. The whole design is in [updates.md](updates.md). It has been run on Windows, on Linux with systemd, on a Mac whose program is a LaunchAgent and on a QNAP NAS. Not yet run: a QNAP after a reboot, and a Mac with nobody signed in.

## Signing

The project does not hand out builds signed with anyone's certificate. Whoever builds `dokkit` for their own machines signs it with their own code-signing certificate if they have one, which is what keeps antivirus quiet about it; an unsigned build works the same. The release workflow signs the macOS files with the certificate held in its repository secrets when those are set, and leaves them unsigned otherwise; the Windows and Linux files are not signed. Whatever the signature, the updater trusts a file only through the signed `SHA256SUMS`. A build is never packed or compressed into a self-extracting file.

## Configuration

`dokkit`'s own configuration lives outside any app repo and is only editable by an administrator on an installed service. It holds:

- the server address, the certificate fingerprint and the machine key
- the folders `dokkit` may read `dokkit.toml` files from
- the spool folder and its size cap

## Not in this design

A listener on localhost. Earlier notes had `dokkit` listening on localhost so apps and the CLI could hand it data. The spool folder covers the CLI, and libraries send straight to the server, so nothing here needs it. It stays possible, and off.

## Built so far

In `program/`: `dokkit init`, `run`, `ping`, `check`, `apply`, `enrol`, `watch`, `folder`, `status`, `doctor`, `service`, `scan`, `propose`, `import seq`, `imessage`, `startup`, `updater` and `version`. With `DOKKIT_URL` and `DOKKIT_KEY` set they use that key; otherwise they use the address and machine key that `dokkit enrol` saved in the user's configuration folder.

`dokkit watch` reads `dokkit.toml` files from the folders in `DOKKIT_FOLDERS` or in the saved configuration, and from the folders directly inside them. It declares each file, runs its `http`, `tcp`, `process` (by name, and with `command_has` by a piece of the executable path on Windows, asked of the system by process number, so Local Service sees other accounts' processes, in the form \Device\HarddiskVolumeN\..., matched after the drive; by a piece of the command line on Linux, from `/proc`, and macOS, from `ps`; a process whose path or command line cannot be read is not a match), `windows-service` and `systemd` checks on their own timing, sends the log files it names, says the machine is alive once a minute, and re-reads a file when it changes. `dokkit status` shows what `watch` last wrote down: the files it reads, when the spool was last emptied, and how much is waiting.

`dokkit watch --background` starts the same program detached, writing to `watch.log` in the spool folder, and does nothing when one is already running (a recorded process number counts only while that process is alive). `dokkit startup on` is for Windows only and adds it to the signed-in person's own startup programs. `dokkit status` shows the process number to stop it by.

An `http` check with `slow` set reports `degraded`, with the time in milliseconds as its value and a note such as "answered in 2.4 s, slower than 2 s", when the answer succeeds but takes longer than `slow`. The server decides when that becomes an issue. `slow` is refused unless the check is `http`, it is more than zero, and it is less than the check's `timeout` (5 seconds when not set). `dokkit check` prints such an answer as `slow` and does not count it as a failure.

`dokkit help`, `dokkit --help` and `dokkit -h` print the command list. `--help` or `-h` after a known command prints that command's help, unless a `--` comes first, and so does the bare word `help` right after any command except `run` and `ping`, so `dokkit scan help` prints help and runs nothing. For `run` and `ping` only the first argument counts, and only as `--help` or `-h`, so a job named `help` is a job.

`dokkit service` works on Windows, on Linux with systemd and on macOS (below). `dokkit service install` on Linux needs root. It uses the address and key saved by the account named in `SUDO_USER`, or else root's own, says which file it used and which address, and when neither has one says what to run. `get.sh` run without root installs to `~/.local/bin`, which `sudo` does not search, so it prints the `sudo` line with the full path. A failed install removes the unit file and the address and key it had written, so it can be run again, and an uninstall carries on past a `systemctl` step that fails and also clears a half install. It makes a system user named `dokkit` with `useradd` (with no login and no home), or stops and says so when `useradd` is not there. It copies the program to `/usr/local/bin/dokkit`, writes the saved address, key and folders to `/etc/dokkit/config.json` (owned by root, readable by the `dokkit` group), writes `/etc/systemd/system/dokkit.service` to run `dokkit watch` as the `dokkit` user with its spool in `/var/lib/dokkit`, then runs `systemctl daemon-reload` and `systemctl enable --now dokkit.service`. The folders in the configuration must be readable by the `dokkit` user, folders above them searchable by it. Install warns about a folder that looks closed to it, and `dokkit status` and the service's log name each folder it cannot list, since it would otherwise find no `dokkit.toml` and say nothing. `uninstall` stops and disables it, removes the unit file, and removes the address and key from the config, keeping the two lists. It does not tell the server: the machine stays enrolled there and shows as stopped reporting until its key is revoked, and `uninstall` says so. As root, or in the `dokkit` group, `dokkit status` and `dokkit doctor` read the service's configuration and spool. `start`, `stop` and `update` run the matching `systemctl` call; `update` first copies the newer program into place. This runs as a service on real Linux machines.

`dokkit service` on macOS runs `dokkit watch` as the LaunchDaemon `dev.dokkit.service` (`/Library/LaunchDaemons/dev.dokkit.service.plist`), so it runs from boot with nobody signed in and keeps running at logout, as a hidden account named `_dokkit` with no login, no shell, no home and no rights, never root. macOS holds a program started by a signed-in user (a LaunchAgent) to the Local Network permission, which a person must allow on the Mac's screen, and answers its connections to other machines on the local network with "no route to host"; it does not hold a daemon started by `launchd`, or a program run as root, to it (Apple's technical note TN3179, quoted by an Apple engineer in the developer forum threads 811712 and 763753, which also say that a daemon "runs in the global login session" and is not subject to the check, and that a role-account daemon with `UserName` is the supported form). So the service needs no allowance in System Settings, signed or not; the signed build still matters for the Messages permission of a per-user copy and for the Local Network permission if the program is run as an agent. `install`, `uninstall`, `start`, `stop` and `update` need root. `install` uses the enrolment of the account that ran `sudo`, or root's, makes the group and user `_dokkit` with `dscl` (a number from 301 up that no user and no group has), copies the program to `/usr/local/bin/dokkit`, writes the saved address, key and folders to `/Library/Application Support/Dokkit/config.json` (owned by root, readable by the `_dokkit` group and no one else; the same file holds the `restart` and `hosts` lists), makes `/var/db/dokkit` for the spool (owned by `_dokkit`, closed to everyone else), copies the waiting reports and log positions of the person's own spool into it, and leaves the originals. Before it starts the service it turns off the person's own LaunchAgents that run `dokkit watch` (`launchctl bootout` and `launchctl disable`, the files left where they are, and the line that turns one on again is printed) and ends a plain background copy that the person's spool names, so two copies never run; if the service does not start, those agents are turned on again. `uninstall` unloads the daemon, removes its plist and the address and key from the configuration, and leaves the `_dokkit` account, the folders and the person's turned-off agents; it says the machine is still enrolled. `start` loads or starts the daemon, `stop` unloads it and `update` copies the newer program into place and restarts it. The service's output is appended to `/var/db/dokkit/service.log`, which nothing trims. Folders it reads must be readable by `_dokkit`, and folders inside a person's Desktop, Documents or Downloads are closed to it by the system, so install warns about a folder that looks closed and `dokkit status` names each one it cannot list. The service cannot send iMessages: only a program in a signed-in user's session can drive Messages, so a Mac that has `dokkit imessage on` stays on its LaunchAgent and `install` stops and says so; moving it to the service means `dokkit imessage off` first. The updater (`updates.md`) looks after the daemon as a system job, restarted with `launchctl kickstart -k system/dev.dokkit.service` and read with `launchctl print system/dev.dokkit.service`. The daemon has not been run on a real Mac yet; the program runs there as a LaunchAgent.

`dokkit doctor` makes one request to the server's ping address with the saved key and says what it found. A certificate whose fingerprint is not the one saved at enrol is named as that, with the line to enrol again if it was renewed on purpose. A name that does not resolve, a port nothing listens on, no answer in ten seconds, a certificate no authority signed or that has expired or is for another name, an address that says `https` for a server speaking plain `http`, a key the server does not know (401), a server that is not a Dokkit server (404) or failing (5xx), and a clock more than 30 seconds from the server's each get their own sentence and a line starting "To fix:"; any of them exits 1, as do reports still waiting after a send. On macOS, a request that fails with "no route to host" to a private or link-local address, or to a name that resolves to one, is named as local network privacy refusing a background program, since the same address answers from Terminal. When the request works, and the saved status says a background copy wrote it in the last three minutes but has sent nothing for ten with reports waiting, doctor says that copy is probably being refused by local network privacy and that the fix is the signed build allowed once in System Settings > Privacy & Security > Local Network, or `dokkit service install`. That second detection is a guess from the status file: a copy that cannot send for another reason looks the same, and the program does not yet write down the error its last send drew.

`dokkit service install` on Windows copies the program to `Program Files\DokkitProgram` and the saved address, key and folders to `ProgramData\DokkitProgram`, which only administrators and the system account can change, then registers a service that starts with Windows, runs as Local Service and restarts a minute after a failure. Local Service may read that folder and write only the spool and the log inside it. It cannot read another account's profile folder, so a `dokkit.toml` kept under `C:\Users\<someone>` is not seen by the service; it starts a stopped service only when that service's own permissions let Local Service. `service install` waits for the service to be running and prints the end of its log when it is not. It refuses to install when `ProgramData\DokkitProgram` already exists and is owned by anyone but administrators or the system account, or holds anything but `config.json`, `spool`, `dokkit.log` and `update`, and says what it found. These folders are the program's alone: the server's installer uses `Program Files\Dokkit` and `ProgramData\Dokkit`, which an earlier program used too. `service install` and `service update` find a program installed there (an administrator-owned `config.json` and `dokkit.exe`), copy only its `config.json`, `spool` and `dokkit.log` to the new folder, point the service at the new `dokkit.exe`, and leave everything in the old folders as it was, saying where the old copies are. The folder is set once, with inheritance off and no `/T`, and what is inside is then reset to inherit from it. From an administrator prompt, `dokkit status` and `dokkit doctor` read that configuration. On other systems, `dokkit watch` runs from a systemd unit.

`dokkit scan` writes `dokkit-proposal.json` in the current folder, and each part has a `--no-` flag (`--no-jobs` leaves the scheduled jobs out).

`dokkit watch` holds a request open to the server and does the work it is given, one run at a time. A name it does not know is answered with a refusal. A result that cannot be delivered is sent again for several minutes. The server ends a run still running after 12 hours, or still queued after a day.

`dokkit enrol` takes the server certificate's fingerprint as a third argument, saves it, and from then on trusts the certificate with that fingerprint and no other. The enrol page shows the fingerprint when the server is started with `DOKKIT_CERT` and `DOKKIT_CERT_KEY` and so serves TLS itself.

`dokkit propose` sends the file a scan wrote. Each minute `dokkit watch` asks the server for the checks added in the interface for its machine and runs them beside the ones in files.

Each minute `dokkit watch` reads the first line of the file a `version_from` names and reports it as that service's version. A `version_from` that is a command is not run: nothing has accepted that command. `version_from`, `[logs] path` and an `expiry` file must stay inside the folder of the `dokkit.toml` that names them, links followed.

Each minute it also sends the machine's processor, memory and disk use as `metric` lines (each disk once: on Windows a fixed drive letter; elsewhere a mounted device, with the volumes of one macOS container, bind mounts and subvolumes of one device counted as the first mount listed, which on macOS is `/`, and with the macOS helper volumes under `/System/Volumes`, the Recovery volume and snap loop devices left out) and fetches the stats document of each service with a `[stats]` section, sending the key from the variable `key_env` names as `X-Stats-Key`. `key_env` must start with `DOKKIT_STATS_`; a file that names any other variable is still read, but no stats request is made for it. The same holds when the variable is not set (or empty) where `dokkit` runs: no request is made, the service is not reported down, and `dokkit` writes a warning log line for the service naming the variable, once an hour. A stats address that is reached and answers badly is reported down. Stats are fetched on their own, with 5 seconds for each address, and never hold back a check. Checks and stats fetches run at once, and logs are sent on their own timer every five seconds, so one slow check holds nothing back. An `expiry` check reads its date from `date_from`: an `https` address or `host:port` for a certificate, or a file whose first line is a date. It is degraded inside 30 days and down once past; days left are shown rounded up, and a bare date lasts through that day (UTC). A certificate is not verified, so a self-signed one is read like any other; only its date is used.

On macOS the memory figure is the share of memory Activity Monitor counts as used: anonymous pages less purgeable ones, wired pages and the compressor's pages, from `vm_stat` and `sysctl -n hw.memsize`. The file cache is not counted, as `MemAvailable` leaves it out on Linux. The processor figure is the busy share of the second sample of `top -l 2 -n 0 -s 2`, a two-second window taken once a minute and not an average over the minute, so it moves more than the Linux figure; reading it holds that minute's report for about two seconds. There is no cumulative tick counter readable on macOS without cgo, and `ps -A -o %cpu` reports a decaying average per process, so neither is used. On one Apple silicon Mac with 64 GB the program read 16.70% memory used where `top` showed 28 GB used, of which 18.8 GB was file cache, and 0.48% processor where `top` showed 0.55% over its own sample.

The installed service starts a stopped Windows service again, and restarts a stopped `systemd` unit (the check's `name`, state from `systemctl show`) with `systemctl restart`, when its service page allows that and the service or unit is named in the `restart` list of `ProgramData\DokkitProgram\config.json`, at most once in ten minutes, and says so: the check's good answer carries the note, and a warning log line for the service says it, since the next good answer replaces the note. The unit's state comes from `systemctl show` (`ActiveState`, `SubState`, `Result`, `NRestarts`) and standard output only. A unit that is `activating`, `reloading` or `deactivating` is reported `degraded` and never restarted, but a unit that is `activating` with `SubState=auto-restart` or a failed `Result` is down (systemd is restarting it after a failure, so nothing is restarted from here), and so is one still busy on the third consecutive check. A restart that takes over 30 seconds is abandoned by the program, and no restart holds up the other checks. `nginx` and `nginx.service` count as one unit. `dokkit watch` under a login never restarts anything; on Linux only the unit that `service install` writes does (the program tells it by `INVOCATION_ID` and `DOKKIT_CONFIG`). A check the server gives for another machine's address is not run unless that address is in the `hosts` list of the same file; this machine's own name, loopback and interface addresses always count. A refused check reports down with a note saying so. Neither list is read from anywhere else, and both stay in the file across an uninstall. On Linux the file is `/etc/dokkit/config.json` and on macOS the service's configuration file (below), read only when root owns it and the folder and nobody else can write to either. This has not been run against a real service or unit yet. The Linux service runs as the `dokkit` user, and systemd refuses that user a restart unless a polkit rule allows it, so a `systemd` check restarts a unit only where `dokkit` runs as root or has such a rule; otherwise it reports down.


`dokkit folder add <path>` puts a folder in the list `dokkit watch` reads (`dokkit.toml` files in it and in the folders directly inside it), `remove <path>` takes one out and `list` shows them. The path is made absolute and for `add` must exist; adding one twice changes nothing. The list is in `folders` in the configuration the watching program reads: the installed service's (`/etc/dokkit/config.json`, or `ProgramData\DokkitProgram\config.json`) when one is installed, otherwise the signed-in person's own. Changing the service's list needs an administrator or root, and without one the command prints the exact `sudo` line with the program's full path; the rest of the file is kept and, on Linux, it stays owned by root and readable by the `dokkit` group. On Linux, `add` warns when the `dokkit` user cannot read the folder. `dokkit watch` reads the list again each minute, so a change needs no restart; `DOKKIT_FOLDERS` still overrides it. The installed service reads `folders` only while the file and its folder cannot be written by anyone but root (an administrator on Windows), the same test the `restart` and `hosts` lists pass, and ignores the list otherwise. `dokkit init` ends with the `dokkit folder add <this folder>` line, with `sudo` and the full path when the service is installed. `dokkit status` run by a member of the `dokkit` group, who cannot read the service's `status.json`, says to run it with `sudo`.
